# ContextOps — 디자인 브리프 v1.0 (Claude Design용)

> 사용 방법: 이 문서 전체를 Claude Design에 붙여넣고 "화면 1부터 순서대로 아트보드를 만들어라"고 지시한다. 각 화면의 콘텐츠는 아래에 적힌 실제 문구·수치를 그대로 쓴다(lorem 금지). 구현 스펙은 `docs/SPEC.md` §9와 대응한다.

---

## 1. 제품과 사용자

- **제품 한 줄:** 팀의 목표·로드맵·기술 결정을 하나의 승인된 AI Context로 만들어 모든 팀원의 Claude Code에 같은 버전으로 배포하고, 로드맵이 실제로 진행되는지를 근거와 함께 보여준다.
- **슬로건:** 팀의 지식과 Claude의 기억을 같은 방향으로.
- **사용자 셋:**
  - 팀장(승인자) — 브라우저만. 가져오기 → 정리 → 발행, Roadmap 확인. 비개발자일 수 있음.
  - 개발자 — 명령 한 줄 설치 후 Claude Code 안에서 sync/propose. 웹은 가끔.
  - 심사위원(게스트) — 링크 열고 3분. 설치 없음. 첫 화면에서 문제를 10초 안에 이해해야 함.
- **감정 목표:** "감시 도구"가 아니라 "팀이 같은 방향을 보게 하는 도구". 사람이 결정하고 시스템이 보증한다는 느낌. 차분하고 정확한 개발자 도구, 화려하지 않음.

## 2. 디자인 원칙

1. **근거가 항상 옆에 있다.** 항목·문장·상태 옆에는 원문/코드 라인/커밋 링크가 붙는다. 근거 없는 숫자·판정은 화면에 없다.
2. **행은 마일스톤이지 사람이 아니다.** Roadmap의 기본 행은 마일스톤. 사람은 클릭해야 보인다. 개인 점수·순위·생산성 표현 금지.
3. **"실시간"이라는 말을 쓰지 않는다.** "마지막 보고: 8분 전, v1.3, applied" 형식.
4. **AI는 후보와 질문을 만든다.** AI 결과 카드는 항상 사람의 선택 버튼으로 끝난다. "AI가 판정했습니다" 같은 문구 금지.
5. **데모도 실제 상태를 숨기지 않는다.** loading/empty/error/오프라인/예산 소진 상태를 정직하게 표시.

- **상태를 색만으로 구분하지 않는다** — 아이콘 + 라벨 텍스트를 항상 병기.
  ★ 왜 — 색각 이상뿐 아니라, 발표 영상·인쇄된 심사 자료에서 색이 뭉갠다.
- `accent` 는 **한 화면에 주요 액션 하나**에만. 보조 버튼은 outline.
- `llm` 은 **AI 산출물에만.** 사람이 정한 것에 이 색이 붙으면 신뢰 경계가 흐려진다.
- 🔴 **`ink-4` 로 읽어야 하는 글자를 그리지 않는다** — 용도가 「비활성」 한 낱말인 이유다.
  비활성 상태(`:disabled`)와 장식(`aria-hidden` 인 `◌`·빈 칸 `—`)에만 쓰고,
  **읽어야 하는 보조 글자는 `ink-3`(`meta`)** 로 그린다.
  ★ 왜 — 카드 바탕(`surface`) 위 대비가 1.6:1 이라 발표 영상·인쇄된 심사 자료에서
  **글자가 없는 것과 같다.** 실제로 다섯 자리가 이 색으로 쌓였고 그중 둘은 제품의 주장
  그 자체였다 — P1 을 설명하는 문장과 P7 을 눈으로 재는 Pack 줄 번호다 (FINDINGS 88).
  이것도 `design-tokens.test.ts` 가 잠근다.
- 🔴 **이 표는 기계가 잠근다.** `apps/web/src/app/globals.css` 의 `:root` 가 이 표와
  **정확히 같아야** 하고, `apps/web/test/design-tokens.test.ts` 가 양쪽을 대조한다.
  화면 코드에 색 리터럴(`#…`·`rgb(`)을 적으면 그 시험이 빨개진다.
  ★ 왜 — 「토큰만 쓴다」는 문서에 적어 두면 반드시 어느 화면 하나가 즉석 색을 찍는다.
  게이트는 문서보다 강하다 (`CLAUDE.md` 「같은 지적이 두 번 나오면 게이트로 올려라」).
  ⚠ `bad-bg` 는 이 표에 없었는데 화면 5·7 의 `bad` 칩이 필요해서 **여기에 먼저 더하고**
  썼다 — ok/warn 에만 배경이 있으면 같은 칩이 상태에 따라 다른 모양이 된다.

### 화면 1 — 랜딩 `/`
목표: 심사위원이 10초 안에 문제를 이해하고, 클릭 하나로 샘플 팀에 들어간다. 스크롤 없이 첫 화면에 A·B·C가 보인다.

**A. 헤드라인** (좌측, 최대 60% 폭)
- 제목: `팀의 지식과 Claude의 기억을 같은 방향으로`
- 부제: `팀장이 승인한 목표·로드맵·결정을 모든 팀원의 Claude Code에 같은 버전으로 배포하고, 로드맵이 실제로 진행되는지 근거와 함께 보여줍니다.`

- 아래 작은 줄: `팀장은 브라우저에서 15분, 개발자는 명령 한 줄.`

**B. Before/After 비교** (우측 40%, 두 열 카드)

> ⚠ 이 절의 예시 문구는 **목업용**이다. 픽스처 정본은 `docs/SPEC.md` §10.1(paylab)이니

  - 프롬프트 줄(모노): `$ 북스택 검색 API, 실제로 검증됐어?`

  - 답 B: `QC결과.md에 8월 4일 검증 완료로 적혀 있습니다.`

  - 하단: `A·B·C 모두 같은 답 · manifest 3f9c2e1a`

**C. 스크롤 아래 섹션 순서**
1. `왜 git으로 안 되나요?` — 세 문장 카드 3개(팀장은 git을 안 씁니다 / 컨텍스트는 레포 하나에 갇히지 않습니다 / git은 "왜"를 모릅니다) + 한 줄 `DeepWiki는 코드를 사람에게 설명합니다. ContextOps는 팀의 결정을 AI에게 꽂습니다.`
2. `어떻게 동작하나요` — 3단계 가로 스텝: ① 만든다(문서·답변·코드 → 승인) ② 배포한다(같은 버전·같은 해시) ③ 진행이 보인다(AI가 근거를 자동 보고, 사람이 완료 확인). 각 스텝 아래 실제 화면 썸네일.
3. `터미널 재생` — 좌: 타이핑되는 터미널(훅 알림 → /contextops:sync → 작업 → 자동 progress) / 우: 같은 타임라인으로 Roadmap 행 BS-M2가 1/3 → 2/3으로 바뀌는 미니 패널.
4. `서버가 아는 것 / 모르는 것` 2열 표 — 아는 것: 팀·프로젝트 ID, 구조화 항목, 문서 원문(팀장이 등록한 것), 경로·줄·커밋, 버전·해시 / 모르는 것: 저장소 코드 본문, 환경변수·secret, 개인 CLAUDE.local.md, Auto Memory, Claude 대화.
5. `개발자 설치` — 코드 블록 1줄 `npx contextops setup` + 아래 "그 다음은 Claude Code에서 /contextops:init 한 번".
6. 푸터: 제출 팀명, GitHub 링크, Known limitations 링크.

**문서↔코드 카드** 예: `재시도 정책 — 문서 5회 / 코드 3회` 우측에 `parking-api · src/payment/retry.ts:14 · MAX_RETRY = 3` EvidenceLink. 버튼: [문서가 맞음(코드 수정 필요)] [코드가 맞음(문서 갱신)] [보류].
**병합 카드** 예: `"PaymentIntent"(api)와 "결제요청"(admin)은 같은 개념인가요?` [같음, 용어: ___] [다름].
> ⚠ **지금 화면의 버튼은 [A만 남김] [B만 남김] [둘 다 보류] [무시]** 다 (탐지 종류 공통 4개).
> 「합침」이라고 적지 않는 것은 실수가 아니다 — 서버가 하는 일은 **진 쪽을 `deprecated` 로
> 보내는 것뿐**이고 이긴 쪽으로 본문도 근거도 옮겨 오지 않는다 (`RESOLUTION_ITEM_OUTCOME`).
> 위의 「같음, 용어: ___」·「다름」은 **아직 담을 칸도 문도 없다** (FINDINGS 72① · 76).
> 진 쪽 `source_refs` 를 이긴 쪽에 이어 붙이는 갈래가 생기면 그때 이 두 줄을 지워라.
**열린 질문 카드**: `MQTT를 선택한 이유가 있나요?` textarea + [답변 저장 → ADR 항목] [담당자 지정].
빈 상태: `결정할 것이 없습니다. 발행할 준비가 됐어요.` [Context로 이동].
