# paylab 결제 서비스 — 팀 목표와 규칙

- 작성: 결제팀 팀장
- 마지막 갱신: 2026-03-11
- 대상 저장소: `paylab-api` (전체)
- 이 문서가 결제팀의 정본이다. 여기와 코드가 다르면 **코드가 틀린 것으로 보고 티켓을 연다.**

---

## 1. 우리가 만드는 것

paylab 은 국내 커머스 가맹점을 위한 결제 대행 서비스다. 가맹점은 우리 API 로 결제를
띄우고, 우리는 뒤에서 PSP(카드사 대행사) 두 곳에 붙는다. 가맹점이 우리를 쓰는 이유는
하나다 — **PSP 가 흔들려도 결제가 흔들리지 않는 것.** 그래서 이 문서의 규칙은 대부분
「밖이 실패할 때 우리가 어떻게 행동하는가」에 대한 것이다.

우리가 안 하는 것도 적어 둔다. 우리는 카드 정보를 저장하지 않는다. 토큰만 받는다.
가맹점 정산은 하루 1회 배치이고 실시간이 아니다.

## 2. 올해의 목표

| | 목표 | 어떻게 재나 | 기한 |
|---|---|---|---|
| G1 | 결제 승인 성공률 99.5% | PSP 장애 구간을 포함한 주간 성공률 | 2026-12-31 |
| G2 | 환불 접수→종결 24시간 이내 95% | `refund.closed_at - refund.created_at` p95 | 2026-12-31 |
| G3 | 정산 오차 0원 | 일 배치 후 원장 대사 차액 | 2026-12-31 |

G1 과 G2 는 서로 당긴다. 재시도를 늘리면 승인률은 오르지만 환불·취소가 늦어진다.
둘이 부딪히면 **G2(고객이 돈을 돌려받는 속도)가 우선이다.**

## 3. 반드시 지키는 규칙 (must)

### 3.1 외부 PSP 호출 재시도

PSP 호출이 실패하면 **최대 5회까지 재시도**한다. 재시도 간격은 **지수 백오프**로
1초 → 2초 → 4초 → 8초 → 16초로 늘리고, 각 간격에 ±20% 지터를 더한다.

**고정 간격 재시도는 금지한다.** PSP 가 흔들릴 때 모든 인스턴스가 같은 박자로 다시
때리면 우리가 장애를 키운다. 2025년 11월 사고가 정확히 그거였다.

재시도 대상은 네트워크 오류와 5xx 뿐이다. 4xx 는 재시도하지 않는다.
멱등키(`Idempotency-Key`)가 없는 요청은 재시도하지 않는다.

### 3.2 환불 SLA

환불 요청은 **접수 후 24시간 안에 종결**한다. 종결은 `승인` 또는 `거절` 둘 중 하나이고,
「검토 중」으로 남아 있는 것은 종결이 아니다.

24시간이 지나도록 담당자가 손대지 않은 건은 **자동으로 승인 대기 큐에서 빠져
에스컬레이션**된다. 기한 없이 `pending` 으로 쌓아 두는 것은 금지다 — 고객이 돈을
언제 받는지 모르는 상태가 우리 CS 비용의 절반이다.

모든 외부 호출에는 타임아웃이 있어야 한다. 기본 5초, 환불 승인 호출만 10초.

### 3.3 로그에 PII 를 남기지 않는다

다음은 **어떤 로그에도** 남기지 않는다. 애플리케이션 로그·접근 로그·에러 리포트·
웹훅 수신 덤프 전부 해당한다.

- 카드번호(마스킹본 포함) · CVC · 유효기간
- 이름 · 생년월일 · 이메일 · 전화번호 · 주소
- PSP 가 내려 주는 원본 payload 통째로

디버깅에 필요하면 **결제 ID 와 이벤트 ID 만** 남기고, 원본은 PSP 콘솔에서 본다.
원본을 꼭 봐야 하면 마스킹 유틸을 거친다.

### 3.4 금액은 정수(원)로만 다룬다

`number` 부동소수 연산 금지. 원 단위 정수로만 더하고 뺀다. 화폐 단위가 늘어나면
그때 최소 단위를 다시 정한다.

### 3.5 웹훅은 서명 검증 후에만 처리한다

서명 검증 전에는 payload 를 파싱하지도 저장하지도 않는다. 검증 실패는 401 로 끊고,
재전송은 PSP 가 알아서 한다.

## 4. 로드맵

### M1 — 재시도·타임아웃 정리 (2026-10-31)

- 경로: `src/payment/`, `src/psp/`
- 완료 기준:
  - PSP 호출 재시도 정책이 공용 모듈 한 곳에만 있다
  - 모든 외부 호출에 타임아웃이 걸려 있다
  - 재시도 횟수와 간격이 설정값으로 빠져 있다 (배포 없이 바꾼다)

### M2 — 환불 SLA 계측 (2026-11-30)

- 경로: `src/refund/`, `src/ledger/`
- 의존: M1
- 완료 기준:
  - 환불 건마다 접수·종결 시각이 남는다
  - 24시간을 넘긴 건이 대시보드에 뜬다
  - 넘긴 건이 자동으로 에스컬레이션된다

### M3 — PII 마스킹과 감사 로그 (2026-12-31)

- 경로: `src/common/`, `src/webhook/`
- 의존: M1
- 완료 기준:
  - 로그로 나가는 모든 객체가 마스킹 유틸을 거친다
  - 웹훅 원본 payload 가 로그에 남지 않는다
  - 누가 언제 환불을 승인했는지 감사 로그에 남는다

## 5. 아직 정하지 못한 것

여기 있는 것은 **결정이 아니다.** 코드로 옮기기 전에 팀에서 답을 먼저 정한다.

- 재시도를 다 쓰고도 실패한 결제를 **자동 취소할지, 수동 확인 큐에 넣을지** 못 정했다.
  자동 취소는 빠르지만 PSP 쪽이 뒤늦게 승인으로 뒤집는 경우가 분기당 몇 건 있다.
- **부분 환불도 24시간 SLA 인지** 정하지 않았다. 전액 환불만 24시간이고 부분은
  더 길게 가자는 의견과, 고객 입장에선 같다는 의견이 갈렸다.
- 웹훅 **재전송을 며칠까지 받아 줄지** 정하지 않았다. PSP 는 3일까지 보내는데,
  우리 멱등 테이블을 며칠 보관할지와 같이 정해야 한다.
- 정산 화폐가 KRW 외로 늘어날 때 **반올림 규칙**을 정하지 않았다. 3.4 는 「그때 다시
  정한다」로 미뤄 뒀는데, 가맹점 두 곳이 이미 USD 정산을 물어봤다.

## 6. 용어

| 말 | 뜻 |
|---|---|
| PSP | 카드사에 붙는 결제 대행사. 우리는 두 곳에 붙는다 |
| 승인(authorize) | 카드 한도를 잡는 것. 돈이 움직이지는 않는다 |
| 매입(capture) | 잡아 둔 한도에서 실제로 돈을 가져오는 것 |
| 종결(closed) | 환불이 승인 또는 거절로 끝난 상태. 「검토 중」은 종결이 아니다 |
| 원장(ledger) | 돈의 움직임을 한 줄씩 append 하는 표. 수정·삭제 없음 |

## 7. 아키텍처 한 장

```
가맹점 → [payment] → [psp] → PSP A/B
              ↓         ↑
          [ledger]   [webhook] ← PSP 콜백
              ↑
          [refund]
```

- `payment` 는 승인·매입을 맡는다. PSP 를 직접 부르지 않고 `psp` 를 거친다.
- `psp` 만이 바깥으로 나간다. 재시도·타임아웃이 사는 자리다.
- `webhook` 은 PSP 콜백을 받아 상태를 맞춘다. 서명 검증이 먼저다.
- `refund` 는 환불을 맡는다. 원장에 반대 부호로 한 줄을 더한다.
- `ledger` 는 append only. 여기서 계산이 틀리면 정산이 틀린다.
