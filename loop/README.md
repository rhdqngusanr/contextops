# loop/ — 자율 개발 루프

이 저장소는 **자기 자신을 만드는 루프**를 갖고 있다. 한 바퀴마다 새 헤드리스
Claude Code 세션이 열려서, 이번에 뭘 할지 문서에서 읽고, 하나를 고치고, 검사하고,
커밋하고, 다음 바퀴를 위해 기록을 남긴다.

## 왜 이렇게 만들었나

### 기억은 대화가 아니라 **파일**에 산다

한 바퀴마다 세션을 **새로** 연다. 대화를 이어 붙이지 않는다.
이어 붙이면 컨텍스트가 부풀고, 20바퀴째의 세션은 1바퀴째가 왜 그렇게 했는지를
**요약의 요약**으로만 안다. 대신 매 바퀴가 `docs/STATUS.md` 와 `FINDINGS.md` 에
**다음 바퀴가 읽을 것**을 쓴다. 그래서 이 두 파일을 갱신하는 게 한 바퀴의 제일 중요한 일이다.

### 목록은 **관통이 만든다**

일을 `STATUS.md` 목록에서만 고르면 **목록에 없는 고장은 영원히 안 보인다.**
그래서 한 바퀴는 `tools/walkthrough.ps1` (import → publish → sync)로 시작한다.
막힌 자리가 곧 이번 바퀴의 일이다.

### 규칙에는 반드시 **왜**를 적는다

금지만 적으면 빠져나갈 길을 찾는다. 이유를 적으면 그 이유를 지킨다.
`PROMPT.md` ③ 의 규칙 표에 「왜」 열이 있는 이유다.

### 같은 지적이 두 번 나오면 **게이트로 올린다**

문서에 적는 것만으로는 안 지켜진다. `tools/principles.ps1` 이 절대 원칙 P1~P7 을
기계로 세는 자리다. **게이트는 문서보다 강하다.**

## 쓰는 법

```bash
# 1. 등록 — PATH·claude.exe 경로를 잡아 작업 스케줄러에 넣는다
powershell -ExecutionPolicy Bypass -File loop/ctl.ps1 install

# 2. 시험 주행 — 파일을 하나도 안 고친다. 턴 수·시간·비용만 잰다
powershell -ExecutionPolicy Bypass -File loop/ctl.ps1 dryrun

# 3. 켜기 — 창을 닫아도, 껐다 켜도 계속 돈다
powershell -ExecutionPolicy Bypass -File loop/ctl.ps1 start

# 4. 지켜보기
powershell -ExecutionPolicy Bypass -File loop/ctl.ps1 status

# 5. 끄기 — 현재 바퀴를 마치고 멈춘다 (작업 중인 커밋이 안 날아간다)
powershell -ExecutionPolicy Bypass -File loop/ctl.ps1 stop
```

> 🔴 **`start` 는 보이는 터미널 창을 띄운다** (사용자 상시 지시 2026-09-06).
> 창이 떴는지 눈으로 확인해라 — **창이 사라진 것이 루프가 멈춘 신호**다.
> ⚠ 그 창을 닫으면 루프도 죽는다. 세울 때는 `ctl.ps1 stop` 을 써라.
> ⚠ 로그아웃·재부팅은 못 넘는다. 스케줄러로 숨겨 돌리면 넘지만, **그건 안 쓰기로 했다** —
> 창 없이 돌 때 조용히 죽은 판을 몇 시간 뒤에야 알아챈 적이 네 번 있다.

> ⚠ `loop.ps1` 을 **직접 실행하지 마라.** 무한 루프라 그 창과 세션이 거기 묶이고,
> 창을 닫으면 같이 죽는다. 작업 스케줄러로 돌려야 로그아웃·재부팅을 넘긴다.

### 밤에 두 번 돌리기

```bash
# 1차가 끝나면 HANDOFF.md 를 INBOX 에 꽂고 2차를 이어 켠다
powershell -ExecutionPolicy Bypass -File loop/relay.ps1 -WatchPid <1차 PID>
```

인계장을 **1차가 죽은 뒤에** 꽂는 이유: `INBOX.md` 는 루프도 고친다. 사람이 미리 적어 두면
1차의 커밋이 덮어쓴다.

```bash
# 자기 전에 한 번 — 인계장만 꽂아 보고 눈으로 확인한다. 루프는 안 켜진다
powershell -ExecutionPolicy Bypass -File loop/relay.ps1 -InsertOnly
```

⚠ 인계장 삽입은 **잘못되면 엉뚱한 조각이 다음 루프의 지시가 되는** 자리다.
밤에 처음 돌려 보는 건 너무 늦다.

## 파일

| 파일 | 무엇 |
|---|---|
| `env.ps1` | 설정만. 로직 없음. 모델·노력·바퀴 상한·비용 상한·브랜치 |
| `env.local.ps1` | `ctl.ps1 install` 이 만든다. PATH·claude.exe 경로. **커밋 안 함** |
| `loop.ps1` | 루프 본체. 한 바퀴 = 새 세션 하나 |
| `ctl.ps1` | 켜기/끄기/상태/시험주행/등록 |
| `common.ps1` | 셋이 같이 쓰는 것(브랜치·HEAD 조회 · **잠금**). **같은 걸 두 곳에 적으면 갈라진다** |
| `relay.ps1` | 1차가 끝나면 인계장을 꽂고 2차를 잇는다. `-InsertOnly` 로 미리보기 |
| **`PROMPT.md`** | **한 바퀴의 전부.** 합격 기준·읽을 문서·규칙·순서·체크리스트 |
| `HANDOFF.md` | 2차 루프 인계장 (사람이 자기 전에 고쳐 둔다) |
| `STOP` | 있으면 현재 바퀴를 마치고 멈춘다. `ctl.ps1 stop` 이 만든다 |
| `.lock` | **누가** 잠금을 들고 있나 (진단 전용). 배타는 이 파일이 아니라 OS 뮤텍스가 한다 |

## 설정을 바꿀 때 — **루프를 세우지 마라**

`env.ps1` 은 **바퀴마다 다시 읽힌다.** 값만 고치면 **다음 바퀴부터** 먹는다.

```bash
# 모델·노력·바퀴 수를 바꾸고 싶다 → env.ps1 만 고친다. 끝.
```

★ 왜 이렇게 됐나 — 전에는 시작할 때 한 번만 읽어서, 값을 바꾸려면 `stop` → `start` 를
해야 했다. **그 사이에 루프가 꺼진 채로 남는 일이 반복됐다** — 사람이 「또 꺼졌다」를
여러 번 발견한 원인의 절반이 이것이었다. **설정을 바꾸는 것과 루프를 멈추는 것은
다른 일**인데 묶여 있었다.

⚠ 갈아탄 모델(한도 대응)은 안 덮는다 — 그건 실행 중 상태지 설정이 아니다.
⚠ `loop.ps1` 자체를 고쳤을 때는 여전히 재시작이 필요하다.

## 멈추는 조건

넷 중 먼저 오는 쪽. 전부 `env.ps1` 에 있다.

| 조건 | 기본값 | 왜 |
|---|---|---|
| `MaxCycles` | 12 바퀴 | |
| `MaxHours` | 12 시간 | |
| `MaxCostUsd` | 0 (끔) | **바퀴 수보다 바퀴당 비용이 진짜 제약이다** |
| `IdleCyclesMax` | 3 연속 빈 바퀴 | 아래 「조용한 실패」 |
| `STOP` 파일 | — | 사람이 세운다 |

사용량 한도에 걸리면 멈추지 않고 `BackoffMin` 만큼 물러섰다가 다시 시도한다
(20분 → 40 → 80 → 120 상한). 그 바퀴는 바퀴 수로 세지 않는다.

## 중복 실행 방지

**두 루프가 같은 저장소에서 동시에 돌면 두 AI 세션이 같은 파일을 고치고 같은 브랜치에
커밋한다.** 한쪽이 남의 반쯤 된 작업을 같이 커밋하거나 둘이 서로를 덮어쓴다.
무인이라 아무도 못 본다.

스케줄러의 `-MultipleInstances IgnoreNew` 는 **작업(task) 중복만** 막는다.
사람이 `loop.ps1` 을 손으로 돌리거나 `relay.ps1` 이 띄운 판은 작업이 아니라서 그대로 뚫린다.
그래서 잠금이 따로 있다.

### 왜 잠금 파일이 아니라 **뮤텍스**인가

잠금 파일은 프로세스가 **강제 종료되면 그대로 남는다.** 그리고 이 루프는 실제로 강제
종료된다 — `Stop-ScheduledTask` · 재부팅 · 바퀴 시간 초과 정리. 그러면 다음 날 아침
루프가 "이미 돌고 있다"며 안 켜지고, 사람이 유령 파일을 손으로 지워야 한다.

**OS 뮤텍스는 프로세스가 죽으면 OS 가 놓아준다.** 지울 것이 없다.
(강제 종료된 주인의 뮤텍스를 잡으면 `AbandonedMutexException` 이 나는데, 예외가 나면서도
**소유권은 넘어온다.** 그 예외를 잡아 정상 획득으로 처리한다.)

`loop/.lock` 파일은 남지만 그건 **잠금이 아니라 진단**이다 — 누가 언제부터 들고 있나를
`ctl.ps1 status` 가 보여주기 위한 것이라, 유령으로 남아도 아무것도 막지 않는다.

### 규칙 넷

| | |
|---|---|
| **저장소마다 따로** | 뮤텍스 이름에 저장소 경로 해시가 들어간다. 다른 프로젝트에서 같은 루프를 동시에 돌리는 건 충돌이 아니다 |
| **DRY RUN 은 안 잠근다** | 파일을 하나도 안 고치니 옆에서 도는 진짜 루프와 안 부딪힌다 — 그게 dryrun 의 존재 이유다. 대신 로그를 `<날짜>_dryNNN.jsonl` 로 갈라 진짜 바퀴 기록을 안 덮는다 |
| **거절은 `exit 0`** | 0 이 아니면 스케줄러가 「비정상 종료」로 보고 3번 다시 켠다. 같은 벽에 세 번 부딪히며 로그만 더러워진다 |
| **고아 세션을 정리한다** | `loop.ps1` 이 강제 종료되면 **자식 `claude` 는 살아남는다.** 뮤텍스는 풀리니 새 루프가 켜지고, 그 옆에서 고아가 같은 저장소를 계속 고친다 — 뮤텍스를 우회한 중복이다. 잠금을 잡은 직후 `.lock` 의 `child_pid` 를 보고 정리한다 |

`relay.ps1` 도 잇기 전에 잠금을 확인하고, 잡혀 있으면 최대 60분 기다린다.

## 조용한 실패를 막는 그물 셋

자율 루프의 진짜 위험은 **에러가 나는 것**이 아니라 **에러 없이 아무것도 안 하는 것**이다.
바퀴는 `OK` 로 기록되고 코드는 그대로다. 로그만 봐서는 모른다.

| 그물 | 무엇을 잡나 |
|---|---|
| **한 줄 명령행** | `Start-Process -ArgumentList <배열>` 은 원소를 공백으로 잇기만 하고 따옴표를 안 씌운다 → 부트 프롬프트가 단어로 쪼개져 `-p` 에 `Read` 한 단어만 들어간다. 세션이 할 일을 못 본 채로 뜬다 |
| **사전 점검** | 스케줄러는 PATH 를 안 물려받는다 → `git`·`node` 를 못 찾고 죽는데 로그에도 안 남는다. 매 바퀴 전에 **직접 불러 본다** |
| **빈 바퀴 감지** | 바퀴마다 커밋이 늘었는지 센다. 연속 3바퀴가 아무것도 안 남기면 벽에 부딪힌 것으로 보고 멈춘다 |

그리고 **사용량 한도 오탐**: `stream-json` 전체에서 `rate.?limit` 을 찾으면 안 된다 —
그 문자열은 사용량 메타데이터의 **필드 이름**으로 늘 들어 있어서, **성공한 바퀴 뒤에도**
20분씩 물러서게 된다. **결과 줄의 에러 문구만** 본다.

## 다른 프로젝트에 옮겨 쓰려면

이 루프는 한 Unity 게임 프로젝트에서 **먼저 몇 주 굴려 본 것**을 ContextOps 에 맞춰
옮긴 것이다. 위의 「조용한 실패를 막는 그물 셋」은 전부 거기서 실제로 밟은 것들이다.
바꿔야 하는 것은 넷뿐이다:

1. **`PROMPT.md`** — 합격 기준 · 읽을 문서 색인 · 규칙과 「왜」 (프로젝트마다 완전히 다르다)
2. **`tools/ci.ps1`** — 검사 층 (그 프로젝트의 「초록」이 무엇인가)
3. **`tools/walkthrough.ps1`** — 관통 시나리오 (그 제품이 「돈다」가 무엇인가)
4. **`env.ps1`** — 모델 · 바퀴 시간 · 브랜치

`loop.ps1`·`ctl.ps1`·`relay.ps1` 은 거의 그대로 쓴다.

⚠ 제일 흔한 실수는 **`PROMPT.md` 를 짧게 쓰는 것**이다. 무인 세션은 물어볼 사람이 없다.
「왜」가 없는 규칙은 지켜지지 않고, 우선순위가 없는 목록은 아무 데서나 시작하게 만든다.
